# CampusCore v0.2.0 — Release Candidate Notes

Status: **Prepared, not yet tagged or released**

CampusCore v0.2.0 consolidates the foundation, academic operations, product-hardening, Android packaging, and browser companion work into the first repository-wide version-aligned release candidate.

## Highlights

- Full ASP.NET Core + PostgreSQL student-management backend with Identity/JWT authorization and audited administrative workflows.
- Responsive React/TypeScript Web/PWA covering the primary CampusCore product workflows.
- Attendance, leave, marks, grading, report cards, timetables, announcements, attachments, search, import/export, and institution/user administration.
- Database-backed readiness, production configuration validation, non-root runtime containers, loopback-safe Compose defaults, and deployment documentation.
- Cross-platform backup/verification/restore tooling with automated recovery drills.
- Browser E2E, WCAG accessibility smoke tests, migration integrity checks, production Compose smoke tests, and web performance budgets.
- Capacitor 8 Android packaging from the shared client, Android-safe runtime behavior, lifecycle/back handling, and debug APK verification in CI.
- Manifest V3 CampusCore Companion preparation with storage-only permission and no host permissions/content scripts.
- Repository-wide version synchronization using the root `VERSION` file.

## Upgrade notes

### Application version

All release surfaces are prepared for `0.2.0`:

- root `VERSION`;
- .NET assembly/package version;
- Web/PWA package/runtime fallback;
- Docker Compose application build default;
- `.env.example` version;
- browser companion package and manifest.

The tagged release workflow rejects tags that do not equal `v0.2.0` while this version is current.

### Database

The API applies committed EF Core migrations at startup. Before upgrading a production environment:

1. create and verify a CampusCore backup;
2. review the `migrations.sql` artifact generated from the release candidate;
3. deploy the API and wait for `/readyz`;
4. deploy/recreate the Web service;
5. exercise representative authenticated workflows.

At this candidate stage the repository still has a short migration history, so future releases with older production schemas must extend upgrade-chain testing beyond clean/idempotent migration checks.

### Configuration

Production mode now fails closed when known development/local placeholders remain in database or signing configuration. `AllowedHosts` must be explicit in production.

Android API access requires an explicit production HTTPS API origin. Production CORS must explicitly include the trusted Capacitor origin when the native shell calls a separately hosted API.

### Backups

Use the scripts under `scripts/` and follow `docs/backup-restore.md`. A recoverable CampusCore backup includes both PostgreSQL and attachment storage.

## Release artifacts expected from tag `v0.2.0`

The GitHub release workflow is prepared to publish:

- `campuscore-api-v0.2.0.tar.gz`;
- `campuscore-web-v0.2.0.tar.gz`;
- `campuscore-companion-v0.2.0.zip`;
- `migrations.sql`;
- `VERSION`;
- `SHA256SUMS.txt`.

The workflow also assembles an Android debug APK as a short-lived verification artifact. It is **not** a signed production Android release artifact.

## Verification gates before tagging

The release commit should have successful checks for:

- backend formatting/build/tests/vulnerability review;
- Web type checking, lint, unit tests, build, audit, and bundle budget;
- Playwright browser E2E and accessibility smoke tests;
- shell/PowerShell operations-script parsing;
- Docker Compose configuration;
- clean/idempotent database migrations;
- migration SQL generation;
- backup/restore round-trip recovery drill;
- production-mode Compose deployment smoke;
- Android project regeneration/debug APK assembly;
- browser companion validation/package check;
- repository-wide version consistency;
- CodeQL/security automation.

Do not create the `v0.2.0` tag merely because version files are aligned; the release candidate is complete only when the required gates are green.

## Known limitations

- `package-lock.json` is not yet committed. Node workflows therefore use `npm install`, not `npm ci`.
- Android Play signing/AAB publication is not configured in Git because signing credentials belong in an approved secret-management process.
- Browser companion store icons, screenshots, listing metadata, and final publication review remain future work.
- Release screenshots still need to be captured from a verified deployed candidate before treating screenshot documentation as complete.

## Rollback

Application rollback and database rollback are separate decisions. Prefer a forward fix for schema/data issues. Use the guarded restore tooling only when restoring the entire selected recovery point is the intended recovery action.

See `docs/release.md`, `docs/deployment.md`, and `docs/backup-restore.md` for the operational procedures.
